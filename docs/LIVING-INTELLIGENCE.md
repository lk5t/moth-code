## Safety boundaries for the new update

- Build/test all new destructive-reset behavior only in isolated deployments.
- Production reset and0.6.0 publication/deployment require separate explicit Owner authorization under the new brief; do not execute them during implementation.
- Full reset previews owned AI storage/DB categories and retained backups. Never traverse user-provided paths or remove accounts, projects, chat, billing, consent, binaries or platform security configuration.
- Existing reversible GENESIS is not evidence of complete deletion. New reset must invalidate outstanding jobs, block automatic reinitialization, verify cleanup and disclose retained/offline copies.

## Phase 8 — Project Intelligence

Existing chunk retrieval and memory classes are reused in private profile databases. Verified `/v1/me` identity binds rotated sessions to the same profile; unavailable identity uses an isolated session cache. Caller-provided identity claims are ignored. Requests bind to the initiating profile; late UI responses are masked after profile/project changes. Project Cloud sharing is now profile-scoped. Coding tasks capture their inference endpoint and refuse to send to a different signed-in account.

Deleting intelligence removes indexed chunks and this project's profile memories, preserves project files, and records a disabled tombstone so background refresh/agent retrieval cannot silently recreate deleted data. Explicit Refresh enables indexing again. Deletion is refused while coding tasks are active. These are local cache deletion guarantees, not forensic deletion of external/device backups.

## Phase 11 — Explicit full native AI reset

Added a separate Owner-only, recently reauthenticated full-reset API and Settings → Account → Advanced Native AI operations UI. The legacy reversible lineage workflow remains available under its explicit retained-model label. Preview inventories only fixed deployment-owned roots (`storage/models`, model `storage/uploads`, native-package `storage/staging`, `lineage`, `evolution`, `coordinator`, `library`, `eval`), database categories, managed GENESIS backups and external originals. Preview does not stop training or delete data. Execution requires the exact typed confirmation and an unexpired Owner-bound reset ID. Backup erasure requires a separate selected scope and exact typed backup confirmation.

Execution persists a recovery fence, pauses evolution, cancels outstanding leases, waits for native HTTP/background work and local checkpoint/exit, stops stable/canary serving, removes owned artifacts and native database records/history, clears model pins and volatile model state, and verifies the empty inventory. Failures remain fenced and resumable using the same reset ID; no replacement model is created. Existing OS run locking serializes erasure/recovery. Settings, accounts/auth, billing/usage, projects, ordinary chat content, consent, signing keys and software are preserved. Only model references are removed from retained chat messages. Normal updates never invoke this operation.

Job IDs and internal release versions remain monotonic after deletion, including SQLite, so stale worker contributions cannot refer to new jobs/models. Worker heartbeat advertises a reset generation; claims require cleanup acknowledgement. Updated workers cancel current work, then remove only locally marked checkpoints belonging to that server/worker credential scope. Unbound legacy and other-scope caches are retained and reported. Offline/older workers remain visibly unacknowledged. Managed backups (unless separately approved), external originals, exported Desktop packages and infrastructure snapshots remain disclosed; completion certifies deployment-owned live storage, **not irreversible erasure of every physical copy**. The supported deployment runs one coordinator/web process; other processes that directly write the same storage must be stopped before an administrative reset. This change does not redesign the server into a multi-replica scheduler.
