# MOTH Code 0.7.0 — GENESIS ASCENSION

0.7.0 builds on the autonomous, distributed Evolution of 0.6.x. What is new, how it behaves, and what
was — and was not — verified.

## One model identity: MOTH 0.0.1, 0.0.2, …

- Every native lineage begins at **MOTH 0.0.1**. The public version advances by one only when a model
  has been deployed and has passed monitoring (a verified upgrade). Experiments, checkpoints and rejected
  candidates never change it; a new lineage (Genesis) starts again at 0.0.1.
- Earlier labels (MOTH 0.01, 0.02 …, which advanced only on capability milestones) are renumbered once
  at start-up, per lineage, in the order the versions were verified. Weights are untouched; the old label
  is kept as `model_version_legacy`; signed model manifests are re-signed. An activity event reports it.
- The active version is shown in the status bar of every section and leads the Evolution card. Internal
  package names (`moth-evolution-v50-e8`) are storage identifiers and are never shown as the model's name.
- Model versions are separate from application versions (this release is MOTH Code 0.7.0).

## Why replies are incoherent — measured

`moth.model.coherence` checks, on the deployed model itself: whether the tokenizer gives back the same
text (plain text, code, accented text), how many tokens per character it needs, and a fixed set of simple
prompts answered greedily and with the serving settings — empty replies, replies that never end, word-pair
repetition, unreadable characters. The verdict names the cause (tokenizer, decoding or training) and is
measured once per model (cached by its weights). A tokenizer that garbles text blocks architecture growth:
a larger model would not fix it. AI → Evolution shows "Replies: …" with sample replies.

Finding: an untrained byte-level model emits invalid byte sequences (unreadable characters) although the
tokenizer round-trips perfectly — the verdict is "needs more training", not "replace the tokenizer".

## Verified synthetic foundation data

Three new sources, generated by MOTH and checked before use (CC0, no download), selected first by Start
Evolution together with the Python standard library:

- **Arithmetic** — answers computed exactly and re-checked from the question text.
- **Simple instructions** — repeat, upper-case, count letters, sort, compare, reverse; the reply is
  produced by the operation itself.
- **Python fundamentals** — small functions, each executed against its tests in an isolated namespace
  (no imports) and kept only if every test passes.

They use the conversation format, so only the answers are learned. Benchmarks (GSM8K, ARC, MBPP) are not
generated; the library build's decontamination still applies.

## AI page

In 0.7.0 the large architecture diagram moved to AI Settings; since 0.7.1 the model has its own **AI → Model** tab (below). The Evolution card
is the compact MOTH Intelligence panel: model and status, objective, active and rollback models, parallel
work, the computing network (MOTH Cloud and every worker), the intelligence check and growth outcomes.

## Self-repair

A training process that is alive but has not advanced for 20 minutes is stopped and resumed from its last
checkpoint (crashes, disconnected workers and untaken jobs were already handled in 0.6.x).

## Limitations

- Dataset download, cleaning and tokenization still run on MOTH Cloud (workers train and evaluate).
- GPU training, multi-GPU and multi-machine speedups were not verified in the development environment
  (no GPU); the distributed speedup was measured with a real worker sharing one 4-core machine (1.88×).
- Capability benchmarks are small fixed sets; differences within sampling noise count as no change.
- The autonomous coding agent is the existing one; its quality is limited by the native model, which is
  small and early in training.


## 0.7.1

**Model tab (AI → Model).** One active model, described only by measurements: the public name (MOTH 0.0.x),
the parameter count counted from the saved weights, layers, dimensions, attention heads and vocabulary,
the latest checkpoint, the tokenizer fingerprint, the internal identifier, deployment status and the
latest verified improvement. The core visual draws one ring per decoder layer (grouped above 12), split
into one segment per attention head; it turns only while a candidate is training and pulses when the
reported training step increases (reduced-motion settings stop both). Capabilities are the held-out
benchmark results of the active model with the change from the rollback model. Lifecycle shows the
active and rollback models (the Owner can roll back after confirming) and a compact version history
that says which versions still keep weights.

**Minimum monitored requests = 0.** The default is 0 and the stored setting is set to 0 once
(`evolution_settings_v071_min_requests`); a value the Owner sets afterwards persists across restarts and
updates. With no user requests the deployment is judged by three passing health checks during the
monitoring window; any failure still rolls back; with requests, error rate and latency are checked.

**Retention.** Unchanged rule, now visible: after a promotion passes monitoring, the active and previous
working model keep their files; older packages are removed and their records kept. To honour "preserve
model weights during upgrades", nothing is removed when the server starts or updates — models left
from older versions are cleaned after the next verified promotion.

**Notifications.** `GET /v1/admin/notifications` and `POST /v1/admin/notifications/read` require the
Owner (403 otherwise). They are a filtered view of real evolution events (promotions, verified
deployments, rollbacks, deployment failures, rejected cycles, milestones, failed experiments, worker
disconnects, self-pauses, stalls, engine errors, cleanup failures, dataset failures).

**What trains MOTH.** AI Settings has one choice with three switches: MOTH Cloud server
(`backends.local_cpu`/`local_gpu`), workers (`backends.workers` and `cloud_workers`) and this computer
(the desktop's participant worker). Placement among them is unchanged (measured speed decides).

**Updates.** Workers: every heartbeat carries the newest eligible worker release; the worker installs it
between jobs at once (the scheduled check is every 15 minutes). Worker releases roll out to every
worker in one stage; a failure rate above the manifest limit still halts the rollout. A failed install
backs off from 5 minutes, doubling up to 6 hours. Cloud agent: the GitHub release list is requested
with `If-None-Match` (a 304 is not counted against GitHub's rate limit), verified manifests are cached
(signatures are still checked every time), and a rate-limit answer is not retried: the agent waits for
GitHub's reset time and uses the last known list. Desktop: hourly checks plus a check when the window
regains focus after an hour; a staged rollout that has not reached this install is a wait, not an error.

**Not done in 0.7.1 (honest limits).** Dataset preparation, tokenization and deduplication still run on
MOTH Cloud, not on workers; there is no new genuine data-parallel training mode beyond the existing
sharded experiments; no new dataset sources were added; GPU and multi-machine performance were not
verified on real hardware. Older workers (0.6.4/0.7.0) ignore the heartbeat announcement and update on
their own schedule (every 30 minutes) — from 0.7.1 on they update at once.


## 0.7.2

**Dataset preparation on workers** (`server/moth_server/intelligence/distributed_prep.py`). When a library
build is tokenized and workers 0.7.2+ are online, each public domain's training records are split into
chunks of 2,000 and offered as `prep_tokenize` jobs (before training jobs, to any CPU or GPU worker).
A worker downloads the chunk and the lineage tokenizer (SHA-256 checked) and runs
`moth.datafactory.build.encode_chunk` — the same function MOTH Cloud uses — returning ids, loss mask,
record offsets and a 16-byte hash per record. MOTH Cloud checks structure (record count, offsets,
lengths, vocabulary bounds) and re-encodes the first, last and four random records, comparing ids,
masks and hashes exactly; any difference refuses the chunk. MOTH Cloud also works the queue itself (it
prepares unclaimed chunks) and after 15 minutes prepares anything still outstanding. Exact duplicates
(same whitespace-normalised text) are dropped when chunks are merged in order; MOTH Cloud's own path
deduplicates the same way, so the result is byte-identical whoever prepared each chunk (tested).
Domains containing user-consented feedback are always prepared on MOTH Cloud.

**MOTH Cloud's built-in worker** (`evolution/cloud_worker.py`). The server enrolls itself once as a
`cloud` worker named "MOTH Cloud server" under the Owner's account and runs the ordinary worker loop in
a background thread, talking to the server in-process. It takes distributed training shards (its
deltas are validated and averaged like anyone's), preparation chunks and evaluation jobs. It pauses
while MOTH Cloud runs a local experiment, follows AI Settings → What trains MOTH (MOTH Cloud server
and Workers both on) and `distributed.cloud_participates`, and stays off once the Owner revokes it.
`MOTH_CLOUD_WORKER=0` disables it. The server bundle now contains the worker package.

**Strategy memory.** Evolution already ranked strategies by accepted improvements, tilted data towards
measured weaknesses and never repeated an identical configuration. Now a strategy with at least four
runs and no accepted improvement is suspended while another strategy produces improvements; it is
never suspended when it is the only option, and it returns when the statistics change.

**New verified sources.** `synthetic-reasoning` (15,000: sequences, orderings from comparisons,
multi-step word problems — each answer re-derived) and `synthetic-language` (15,000: plurals,
opposites, alphabetical order, word counts, sentence casing from checked tables), CC0, generated
locally.

**Interface.** Views rise in when switched, tab content fades in, loading states use skeletons, and
every button has the same press and keyboard focus feedback. All motion stops under reduced-motion.

**Still limited (honest).** Physical GPU training and multi-machine throughput have not been measured
on real hardware (no GPU is available in this environment); the code paths are the same as on CPU and
are covered by tests. Workers already installed at 0.6.4/0.7.0 update on their own 30-minute schedule;
the immediate update announcement works from 0.7.1. Preparation jobs need workers 0.7.2 or newer.
